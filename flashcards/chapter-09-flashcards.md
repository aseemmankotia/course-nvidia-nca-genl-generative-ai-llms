## Chapter 9: Putting It All Together—Real-World LLM Application Architecture — Flashcards

| # | Front (Question) | Back (Answer) |
|---|-----------------|---------------|
| 1 | When should you choose fine-tuning over prompt engineering? | Fine-tune when: (1) You have >1,000 high-quality labeled examples, (2) Task requires consistent formatting/style, (3) Domain-specific terminology must be learned, (4) Latency budget allows larger upfront cost. Exam tip: <500 examples → prompt engineering; >5,000 examples → definitely fine-tune. |
| 2 | What are the three main cost drivers in LLM production and their optimization techniques? | 1. Compute: Use quantization (4-bit/8-bit), smaller models, GPU sharing. 2. Token processing: Implement caching (30-70% hit rate typical), batch inference, reduce context length. 3. Model hosting: Use spot instances, autoscaling, multi-tenancy. Exam tip: Caching gives biggest immediate ROI for repetitive workloads. |
| 3 | 7B model vs 70B model: latency and throughput differences on single A100 GPU? | 7B: ~50-100ms latency, ~2,000 tokens/sec throughput. 70B: Doesn't fit on single A100 (needs 4-8 GPUs), ~500-1000ms latency, ~200-500 tokens/sec per GPU. Exam tip: 10× parameters ≠ 10× latency; memory bandwidth becomes bottleneck. For <100ms latency, use ≤13B models. |
| 4 | What is the hybrid RAG + fine-tuning pattern and when to use it? | Fine-tune for core task competency + RAG for long-tail knowledge. Use when: (1) Task has consistent patterns (fine-tuning) + evolving facts (RAG), (2) Have labeled data for task but not all knowledge, (3) Need both consistency and freshness. Example: Customer support bot fine-tuned on conversation style, RAG over product docs. |
| 5 | What are the three critical production monitoring metrics for LLM applications? | 1. Task Success Rate (completion rate, accuracy on eval set). 2. Latency (P50, P95, P99—watch P99 for SLA). 3. Cost per request (tokens × pricing). Also log: output quality scores, user feedback, error rates. Exam tip: P99 latency matters most for SLA; median latency can hide problems. |
| 6 | Quantization: 4-bit vs 8-bit trade-offs for inference? | 4-bit: ~4× memory reduction, ~3-4× speedup, 5-10% quality loss (MMLU score drop). 8-bit: ~2× memory reduction, ~2× speedup, <2% quality loss. Exam tip: For creative tasks (dialogue, writing) use 8-bit; for classification/extraction use 4-bit. 4-bit requires calibration data. |
| 7 | What causes high test accuracy but low production accuracy after fine-tuning? | Distribution shift: training/test data don't match production queries. Common causes: (1) Training data too narrow (limited scenarios), (2) Temporal shift (user behavior changed), (3) Geographic/demographic mismatch. Solution: Monitor performance by subgroup, collect diverse production samples, consider prompt engineering + RAG for edge cases. |
| 8 | Model parallelism vs model replication for scaling LLM inference? | Model parallelism (tensor/pipeline): Split single model across GPUs. Use for: models too large for 1 GPU (>40GB). Latency: +20-50ms overhead. Throughput: Limited by slowest GPU. Model replication: Multiple complete model copies across GPUs. Use for: high throughput, low latency. Latency: No overhead. Throughput: Linear scaling. Exam tip: Replication scales better for latency-sensitive apps. |
| 9 | What are the two main approaches to reduce LLM inference latency below 100ms? | 1. Use smaller models (≤7B parameters) + quantization (8-bit) + GPU. 2. Speculative decoding: Draft model generates candidates, larger model verifies (2-3× speedup). Also: Reduce batch size (trades throughput for latency), optimize KV cache, use faster hardware (A100→H100). Exam tip: Can't achieve <100ms P99 with >13B models on typical setups. |
| 10 | When does A/B testing make sense vs immediate full deployment of an LLM improvement? | A/B test when: (1) Impact unclear (new prompt template, different model), (2) Risk of degradation (changing retrieval, fine-tuning approach), (3) Need quantitative comparison. Full deployment: Bug fixes, clear improvements (caching, quantization with validated quality). Exam tip: Always A/B test changes affecting output content/quality. |
| 11 | Semantic caching for LLM applications: typical hit rate and when it's effective? | Typical hit rate: 30-70% depending on query diversity. Effective when: (1) Queries are repetitive (customer support, common questions), (2) Exact match not required (embedding similarity threshold ~0.85-0.95), (3) Outputs don't need real-time data. Use cosine similarity on query embeddings. Exam tip: Caching is cheapest optimization; try first before fine-tuning/model changes. |
| 12 | What is the recommended train/val/test split for LLM fine-tuning with limited data (<5,000 examples)? | With <5,000 examples: 70% train, 15% validation, 15% test OR 80/10/10. Must have validation set to prevent overfitting. With >10,000 examples: 80/10/10 or 90/5/5. Exam tip: Never use 100% for training—always hold out validation set. Test set should reflect production distribution, not just training distribution. |
